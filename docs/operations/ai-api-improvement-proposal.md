# 장고야 부탁해 AI API 성능과 비용 개선안

가장 먼저 비용 계측을 보완하고, 사진 인식과 요리 추천에서 `gpt-6-luna`를 현재 모델과
비교하는 방안을 권고합니다. 품질 기준을 통과하면 저비용 모델을 확대하고, 복잡한 요청에는
현재 추천 모델을 유지합니다. `gpt-6.1-sol`은 품질 개선을 확인하기 위한 비교 후보입니다.

이 문서의 진단은 제안 시점의 상태입니다. 우선 구현 결과와 현재 검증 상태는
[모델 평가 실행 안내](ai-model-evaluation.md)에 기록합니다. 기준은 저장소 코드와 로컬 API 설정이며, 운영 서버의
실효 설정·최근 청구 내역·실측 응답 시간은 확인되지 않았습니다. 아래 절감률은 가정에
따른 계산으로, 실제 절감률이나 성능 개선을 보장하지 않습니다. 적용 정책은
[수익화 운영 기준](../monetization.md), [출시 범위](../product/release-scope.md),
[개인정보 선언](../store-privacy-declarations.md)을 따릅니다.

## 제안 시점의 연동과 개선 지점

- 공급자와 방식: 두 기능 모두 서버의 OpenAI `responses.parse`와 Structured Outputs,
  공유 Zod 계약을 사용합니다. 새로운 Responses API 전환 작업은 필요하지 않습니다.
- 요리 추천: 로컬 `apps/api/.env`의 모델은 `gpt-5.4-mini`이며 코드 기본값도 같습니다.
  상위 모델 비교용 사용자별 고정 분배가 이미 있고, 후보 비율의 기본값은 0입니다.
  [모델 분배](../../apps/api/src/modules/recipes/recipe-model-rollout.ts)를 재사용할 수 있습니다.
- 사진 인식: 로컬 API 설정은 `gpt-4.1-mini`지만
  [서비스 코드](../../apps/api/src/modules/inventory/inventory-photo-parse.service.ts)의
  기본값과 staging 예시는 `gpt-5.6-luna`입니다. 실험의 대조군은 해당 환경의 실제 모델로
  고정해야 합니다. 루트 `.env`에는 별도로 `gpt-5-mini`가 있어 실행 위치와 상속 환경도
  확인해야 합니다. [API 환경 로딩](../../apps/api/src/app.module.ts)은 실행 위치의 `.env`를
  사용하며 이미 설정된 프로세스 환경이 영향을 줄 수 있습니다.
- [추천 생성](../../apps/api/src/modules/recipes/recipes.service.ts)은 추천 3개를 만들고,
  의미 검증 실패 시 같은 모델로 전체 결과를 최대 두 번 더 생성합니다. 이전 실패 결과를
  다음 입력에 포함하므로 보정 호출은 첫 호출보다 비쌀 수 있습니다. 완료 기록 재사용은
  동일 idempotency key에 대한 것이며 새 요청의 결과 캐시는 활성화되어 있지 않습니다.
- 추천 출력 한도는 코드 기본 3,500토큰, staging 예시 2,500토큰입니다. 사진은 1,800토큰이며
  최대 30개 후보를 요청합니다. 임의로 한도를 낮추면 JSON 잘림과 실패가 늘 수 있습니다.
- 두 서비스의 OpenAI 클라이언트에 timeout과 maxRetries를 지정하지 않았습니다. 설치된
  SDK 기본값은 요청당 10분 timeout, 자동 재시도 2회입니다. 추천의 의미 보정 3회와 합쳐지면
  특정 오류 상황에서 HTTP 시도가 최대 9회에 이를 수 있습니다. 이는 정상 요청의 호출 수가
  아니며, 모든 HTTP 시도가 청구된다는 의미도 아닙니다.
- [원가 계산](../../apps/api/src/common/openai-model-config.ts)은 일반 입력·캐시 읽기·출력만
  반영합니다. GPT-5.6 이후의 캐시 쓰기 요금은 집계하지 않습니다.
- [구독 원가 가드레일](../../apps/api/src/modules/monetization/unit-economics-guardrail.ts)과
  [Admin 집계](../../apps/api/src/modules/admin/admin-monetization.service.ts)는 성공 결과 중심입니다.
  실패한 유료 호출 비용까지 포함한 원가 지표가 별도로 필요합니다.

## 모델 비교와 가격 가정

2026년 10월 8일 확인한 공식 단가입니다. 단위는 100만 토큰당 USD이며 Standard의 짧은
컨텍스트 가격입니다. 사진의 청구 입력 토큰에는 이미지 입력을 포함합니다.

- `gpt-5.4-mini`: 일반 입력 $0.75, 캐시 읽기 $0.075, 출력 $4.50.
  현재 추천 대조군입니다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini)
- `gpt-4.1-mini`: 일반 입력 $0.40, 캐시 읽기 $0.10, 출력 $1.60.
  로컬 사진 대조군입니다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-4.1-mini)
- `gpt-5.6-luna`: 일반 입력 $0.20, 캐시 읽기 $0.02, 캐시 쓰기 $0.25, 출력 $1.20.
  현재 코드에 등록되어 있는 사진 기본값이자 신규 모델 접근이 어려울 때의 비교 후보입니다.
  [모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-luna),
  [캐시 쓰기 요금](https://developers.openai.com/api/docs/guides/prompt-caching)
- `gpt-6-luna`: 일반 입력 $0.10, 캐시 읽기 $0.01, 캐시 쓰기 $0.125, 출력 $0.50.
  이미지 입력·Structured Outputs와 `reasoning.effort: none`을 지원하므로 두 기능의
  저비용 비교 후보로 적합합니다. 실제 한국어 품질은 별도 검증합니다.
  [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna)
- `gpt-6.1-sol`: 일반 입력 $2.00, 캐시 읽기 $0.10, 캐시 쓰기 $2.50, 출력 $10.00.
  `none`은 지원하지 않으며 `low`부터 지원합니다. 어려운 요청의 품질 비교 후보로 한정하고,
  reasoning 토큰 비용과 JSON 출력에 남는 토큰 한도를 함께 측정합니다.
  [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol)
- 기존 추천 후보 `gpt-5.6-terra`: 일반 입력 $2.00, 캐시 읽기 $0.20, 캐시 쓰기 $2.50,
  출력 $12.00. 전면 전환은 가격 개선안이 아닙니다.
  [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-terra)

계산 예시는 추천 1회에 입력 3,000·출력 2,000토큰, 사진 1회에 입력 1,500·출력
600토큰을 가정합니다. 재시도·캐시 읽기·reasoning·지역 할증·세금·환율은 제외합니다.
캐시 쓰기는 0토큰인 경우와 입력 전체인 경우를 범위로 표시합니다.

- 추천: 현재 모델 $0.01125 → GPT-6 Luna $0.00130~$0.001375. 약 87.8~88.4% 절감.
- 사진: 현재 로컬 모델 $0.00156 → GPT-6 Luna $0.000450~$0.0004875. 약 68.8~71.2% 절감.
- 코드 기본 사진 모델 GPT-5.6 Luna는 같은 조건에서 $0.001020~$0.001095입니다.
- 월 추천 10,000회와 사진 5,000회: 현재 로컬 설정 기준 $120.30 → 두 기능에 GPT-6 Luna를
  사용하는 경우 $15.25~$16.19. 약 86.5~87.3% 절감입니다.
- 저비용 추천 후 5%에서 현재 mini를 한 번 추가 호출한다고 가정하면 추천 비용은
  $0.0018625~$0.0019375, 약 82.8~83.4% 절감입니다. 실제 보정 입력 증가와 실패 비용은
  별도로 더해야 합니다. 5%는 관측값이 아닌 예시입니다.

이미지는 모델마다 토큰 환산 규칙이 달라 **같은 사진에서 같은 입력 토큰 수가 나온다고
가정할 수 없습니다**. 사진 절감률은 단가 비교이며, 채택 판단에는 동일 사진을 실제 처리한
usage와 청구 비용을 사용합니다. 상위 모델의 추가 reasoning 출력도 위 계산에 포함되지
않습니다. [이미지 처리 기준](https://developers.openai.com/api/docs/guides/images-vision)

## 실행 우선순위

### 1. 비용 계측과 모델 설정을 먼저 보완

신규 모델을 환경변수로 지정하기 전에 가격 레지스트리, 모델별 reasoning 지원표, production
환경 검증을 함께 보완합니다. 현재 레지스트리는 GPT-6을 지원하지 않고, reasoning helper는
`gpt-5`에만 `none`을 지정하므로 모델명만 바꾸면 검증 실패 또는 기본 reasoning 사용으로
이어집니다. 설치된 SDK 타입에는 새 캐시 필드가 없어 공식 API와 호환되는 버전을 확인해야
합니다. 타입 단언으로 새 필드를 신뢰하지 않고 공유 계약·검증을 함께 갱신합니다.

`usage.input_tokens_details.cache_write_tokens`를 저장하고 일반 입력에서 읽기·쓰기를 모두
빼서 과금합니다. 요금은 다음 네 항목으로 계산합니다.

```text
USD = (일반 입력 토큰 × 입력 단가
     + 캐시 읽기 토큰 × 읽기 단가
     + 캐시 쓰기 토큰 × 쓰기 단가
     + 출력 토큰 × 출력 단가) / 1,000,000
일반 입력 토큰 = 전체 입력 토큰 - 캐시 읽기 토큰 - 캐시 쓰기 토큰
```

캐시 쓰기는 일반 입력 요금에 추가로 1.25배를 더하는 방식이 아닙니다. 해당 토큰의
일반 입력 단가를 쓰기 단가로 대체합니다.
[공식 계산 기준](https://developers.openai.com/api/docs/guides/prompt-caching)

`RecipeAiGenerationEvent`와 `InventoryPhotoParseEvent`의 성공·실패 비용을 함께 집계해
**유효 완료 1건당 원가 = 성공·실패·보정의 총 공급자 비용 / 유효 완료 수**를 계산합니다.
SDK 타임아웃 등으로 usage를 받지 못한 호출은 0원 확정으로 보지 않고 미확인 비용으로
분리하며 공급자 청구와 대조합니다. 기존 성공 차감 정책은 유지합니다.

측정은 모델·프롬프트 버전·기능·사진 장면별로 분리하고 평균/P95 비용, P50/P95 응답 시간,
첫 생성 통과율, 최종 성공률, 보정 비율, 토큰 캐시 읽기 비율을 확인합니다. 과거 캐시 쓰기
토큰을 복원할 수 없는 기록은 정밀 원가로 소급 표시하지 않습니다. Prisma 변경 시 새
migration·serializer·shared contract·seed·테스트를 같은 변경에 포함합니다.

### 2. 사진 모델부터 비교하고 단계적으로 확대

현재 사진 모델과 `gpt-6-luna`, 코드 기본 `gpt-5.6-luna`를 동일한 영수증·냉장고 사진으로
비교합니다. 사진 모델에는 추천과 같은 후보 분배가 아직 없으므로 장면별 결과를 기록할 수
있는 고정 사용자 분배를 추가한 뒤 5% → 25% → 50% → 100%로 확대합니다.

상품명·수량·날짜의 정답과 누락·오인식률을 측정합니다. 모델이 출력한 confidence는
정확도의 정답으로 사용하지 않습니다. 날짜가 없으면 null을 반환하고 후보를 사용자가
검토하는 현재 흐름을 유지합니다. 이미지 원본의 저장 정책도 유지합니다.

서버는 현재 EXIF 제거만 하고 해상도 조정은 하지 않습니다. 모바일은 품질 0.7로 이미지를
선택합니다. 장면별 해상도·회전 보정 실험을 별도로 진행하되 영수증의 작은 한글을 먼저
보존합니다. JPEG 용량 감소가 이미지 토큰 절감과 동일하지 않으므로 바이트 수와 청구 입력
토큰을 따로 비교합니다. 한국어·작은 글자·회전된 텍스트는 공식 Vision 문서에도 제한으로
안내되어 있습니다. [Vision 제한](https://developers.openai.com/api/docs/guides/images-vision)

### 3. 추천은 품질을 통과한 요청부터 저비용 모델 적용

현재 추천을 대조군으로 두고 `gpt-6-luna`의 `none` 설정을 기존 후보 분배에서 평가합니다.
초기에는 일반 가정식 요청부터 적용하고, 알레르기·제한 식단 또는 복합 제약 요청은 현재
mini에 유지합니다. 제약이 있는 요청도 전환하려면 별도 평가군 기준을 통과해야 합니다.

저비용 결과가 기존 검증에 실패한 경우 현재 mini로 한 번 보정하는 방안을 비교합니다.
보정 횟수 감소는 최종 성공률을 유지할 때만 채택합니다. 스키마 오류·재고량 초과·단위
불일치·미선언 재료·알레르기 검증을 완화하지 않습니다. 모델이 섞인 호출의 비용은 각
모델 단가로 합산하고 시도별 모델과 usage를 남겨야 합니다.

추천 3개, 전략 구분, 4~8개 조리 단계, 실제 분량·불 세기·시간·안전 문구는 보존합니다.
출력 한도를 일괄 축소하기보다 프롬프트의 중복 표현과 불필요한 설명을 줄입니다.

`gpt-6.1-sol/low`는 어려운 평가군에서 별도로 비교합니다. 상위 모델은 첫 통과율 개선으로
보정 비용을 상쇄하는지 확인한 뒤 채택합니다. 위 토큰 가정에서 Sol은 $0.026~$0.0275로
현재 mini 한 번보다 비싸며, 현재 mini 세 번의 $0.03375보다 낮지만 reasoning·보정 입력
증가를 포함해야 합니다. 이것만으로 일반 추천 전환을 정당화할 수는 없습니다.

### 4. 프롬프트와 캐시는 검증을 보존하며 최적화

추천 입력·보정 JSON의 들여쓰기를 제거하고 정적 규칙과 요청별 값의 중복을 줄이는 실험을
합니다. 정확한 절감액은 토큰을 측정합니다. 재료는 이미 최대 30개로 제한되어 있으므로
추가적인 재료 삭제를 기본 절감안으로 삼지 않습니다.

재고별 ID·단위·수량을 연결한 동적 schema는 잘못된 사용량을 막는 현재 장점입니다.
캐시를 위해 이 결합을 풀지 않습니다. 동적 schema는 Structured Outputs 지시의 일부여서
같은 프롬프트 문구라도 캐시 prefix가 달라질 수 있습니다. 먼저 cache diagnostics로
미스를 확인하고 정적 지시의 위치와 안정성을 개선합니다. GPT-5.6 이후는 정적 prefix에
explicit breakpoint를 두고 변동 suffix 쓰기를 줄이는 실험이 가능합니다. 최소 캐시 길이를
충족하는지 확인하고 채택 전에는 실제 read/write 토큰으로 순이익을 계산합니다.
사용자별 캐시 키 변경은 개인정보 분리와 영향을 검토한 뒤 수행합니다.
[캐시 기준과 진단](https://developers.openai.com/api/docs/guides/prompt-caching)

새 추천 요청을 이전 결과로 대체하는 결과 캐시는 개인화·다양성·차감 의미가 바뀔 수 있어
이번 기본안에서 제외합니다. 이미 있는 idempotency 재사용은 유지합니다.

### 5. 지연 상한과 오류 재시도를 명시

OpenAI 호출별 timeout, 전체 작업 deadline, 재시도 상한을 함께 둡니다. 초기 실험값은
사진 전체 30~45초, 추천 전체 45~60초이며 대조군 P95를 확인해 조정합니다. 이는 관측된
현재 응답 시간이 아닙니다. 남은 deadline 안에서만 보정하거나 짧은 일시 오류를 재시도하고,
SDK와 애플리케이션 재시도가 중첩되지 않도록 한 계층에서 제어합니다. 임의의 타임아웃
재시도를 무료 호출로 가정하지 않습니다.

현재 UI와 API envelope를 유지하는 서버 개선을 먼저 적용합니다. 스트리밍은 검증된
완성 결과를 확정하는 시점·공유 계약·모바일 흐름에 영향을 주므로 별도 요청 범위로 둡니다.
Batch는 50% 할인이 있지만 완료 창이 최대 24시간이라 실시간 추천·사진 등록에는 적합하지
않습니다. 원본 사진을 오래 보관하는 배치 평가도 현재 폐기 정책과 충돌하므로 제안하지
않습니다. 합성 텍스트 평가 등 즉시 결과가 필요 없는 별도 작업에서만 검토합니다.
[Batch API](https://developers.openai.com/api/docs/guides/batch)

## 품질 평가와 채택 기준

아래 수치는 제안하는 실험 기준이며 현재 성능을 나타내지 않습니다.

1. 운영 환경의 실효 모델·output 한도·가격 버전과 최근 14일 이벤트를 확인합니다.
   성공·실패·보정·usage 미확인 호출을 포함하고 모델별 P95를 계산합니다.
2. 추천 200개 조건을 같은 입력으로 모델마다 3회 평가합니다. 재료 1개/30개, 적은 수량,
   ea/ml/g, 짧은 조리 시간, 조리도구 부족, 한국식 재료, 최근 메뉴 중복, 알레르기·제한
   식단을 층별로 포함합니다. 기존 검증과 사람이 평가하는 조리 가능성을 함께 봅니다.
3. 사진 200장(영수증 100, 냉장고·찬장 100)을 2회씩 비교합니다. 실제 사용자 사진을
   원본 보관용으로 수집하지 않고, 검증용으로 허용된 별도 샘플 또는 합성 사진을 사용합니다.
   흐림·반사·긴 영수증·회전·포장 날짜·겹친 상품을 포함하고 정답 항목을 작성합니다.
4. 비용 채택 기준은 **총 비용/유효 완료**가 대조군보다 최소 30% 낮고, 최종 성공률 하락이
   1%p 이내인 것입니다. 추천의 조리 가능성 평가와 사진 항목 F1은 각각 2%p 이상 하락하지
   않아야 합니다. 평균뿐 아니라 제약·장면별 결과와 신뢰구간을 확인합니다.
5. 평가 중 알레르기 위반, 재고 단위·수량 위반의 검증 우회, 근거 없는 날짜 확정이 한 건이라도
   발견되면 해당 후보 확대를 중단합니다. 유한한 평가에서 0건은 절대적인 안전 보장이 아닙니다.
6. 속도 목표는 P95 응답 시간 20% 개선입니다. 가격 목표만 통과하는 후보도 P95가 대조군보다
   10% 이상 악화하면 확대하지 않습니다. 상위 모델의 품질 실험은 가격 절감안과 별도로 판단합니다.
7. 통과 후 기능별 5%부터 최소 7일·유효 완료 500건을 관찰하며 확대합니다. 사진은 장면별로
   판단합니다. 표본이 부족하면 기간을 연장하고, 권한·스키마·안전 문제가 생기면 즉시 대조군으로
   복귀합니다. 새로운 후보 실험 전 기존 후보 트래픽을 확인합니다.

구독 검토에는 기존의 `60 × 추천 P95 원가 + 30 × 사진 P95 원가`와 기본 월 858원 예산을
사용합니다. 실제 환율 설정과 실패 원가를 함께 검토하고, 활성 구독자의 약정 한도·가격·광고
노출·성공 차감 정책을 원가 절감 수단으로 변경하지 않습니다.

## 구현 묶음과 검증

- 1차: 모델 능력·가격·cache-write usage, 실패 비용 지표. 관련 API/shared 계약 테스트와
  새 migration의 깨끗한 DB 검증을 포함합니다.
- 2차: 사진 후보 분배와 추천 저비용 후보 평가. 성공·거부·경계값, 소유권·동의·예약 반환·
  idempotency 중복 차감 방지, 모델 혼합 비용, timeout과 출력 잘림 테스트를 포함합니다.
- 3차: 통과한 프롬프트 축약과 deadline 제어. 기존 추천 검증 데이터로 회귀를 확인하고,
  모바일 UI를 변경하는 경우에만 디자인 시스템 검토·화면 테스트·전후 캡처를 추가합니다.
- 각 구현 완료 시 `pnpm docs:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`를 실행합니다.
  실제 API 평가와 운영 rollout은 이 제안 채택 후 별도 실행 작업입니다.

다른 공급자로 옮기는 방안은 현재 개인정보 고지·공급자 계약과 앱 계약 변경까지 필요합니다.
같은 공급자 내 개선의 효과를 먼저 확인하고, 목표를 달성하지 못할 때 별도 공급자 비교로
확장하는 편이 이 저장소의 현재 범위에 맞습니다.
