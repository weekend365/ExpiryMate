# 장고야 부탁해 디자인 시스템

이 문서는 모바일 앱과 Admin의 **행동·구성·접근성 규칙** 정본이다. 실제 디자인 값은
[`packages/shared/src/design`](../packages/shared/src/design)에 두며, 문서에 hex나 px 값을
복제하지 않는다. 캐릭터 제작 규칙은
[`JANGO_CHARACTER_STYLE_GUIDE.md`](./JANGO_CHARACTER_STYLE_GUIDE.md), 화면 크기·글자 크기별
검증은 [`mobile-responsive-qa.md`](./mobile-responsive-qa.md)를 따른다.

## 1. 목표와 우선순위

디자인 의사결정은 아래 변경 범위·보존 기준 안에서 다음 순서로 평가한다. 사용성 목표의
우선순위가 기존 디자인과 탐색 구조를 임의로 교체할 권한을 주지는 않는다.

1. 사용자가 현재 상태와 다음 행동을 즉시 이해하는가
2. 접근성, 개인정보, 법적 고지와 안전 요구를 충족하는가
3. 핵심 작업을 적은 판단과 조작으로 끝낼 수 있는가
4. 모바일과 Admin에서 같은 의미가 같은 방식으로 보이는가
5. 장고의 친근한 브랜드 경험을 더하는가

접근성·권한·데이터·결제·개인정보·법적 요구는 디자인 변경에서도 유지한다. UI 행동·구성은
이 문서, 캐릭터 형태·제작은 캐릭터 전문 문서, 반응형 검증은 반응형 전문 문서를 따른다.
실제 값과 구현은 공유 토큰·공통 컴포넌트에서 관리한다. 화면별 초안이나 아카이브는 각 역할의
정본을 덮어쓰지 않는다.

### 모바일 변경 범위와 기존 UI/UX 보존

모바일 디자인 작업의 기본값은 **기존 UI/UX를 유지하면서 v18 크레파스 표현을 더하는 것**이다.
가독성·단순화·브랜드 통일 원칙은 기존 화면을 재구성하는 포괄적 허가가 아니다. 신규 화면도
기존 앱의 시각 언어와 탐색 패턴을 이어받는다. Admin은 기존 기준을 유지한다.

보존 기준점은 앱 개편을 되돌린 `e737eb54f1b2bddacadfc078b5287802f418acdc`의 모바일 UI/UX다.
이후 명시적으로 채택한 변경은 해당 범위의 기준을 갱신한다. 작업 시작 시 현재 화면과 원래
기준의 차이를 확인하며, 과거 시안·폐기된 개편 계획을 현행 기준으로 사용하지 않는다.

- **탐색과 흐름:** 현재 홈·추천·보관함·장보기·설정의 5개 탭, 순서·이름·진입점,
  등록 단계·복귀·취소·실행 취소, 기존 경로·딥링크와 기능 접근을 보존한다.
- **정보와 조작:** 화면별 정보 묶음과 순서, 목록의 정보 밀도, 바로가기·필터·버튼의 노출과
  위치를 보존한다. 주요 행동을 강조한다는 이유로 다른 행동을 숨기거나 단계를 늘리지 않는다.
- **시각적 특징:** 배경 일러스트의 장면·구도, 카드의 역할·형태·묶음, 말풍선, 타이포그래피
  위계, 여백의 리듬, 상태색의 의미와 장고 배치 관계를 보존한다.
- **서비스 동작:** 인증·권한·데이터·결제·광고·구독·입력 보존·접근성 정책을 유지한다.
  원화 MASTER의 바이트·비율·얼굴·장갑·입 규칙은 별도 캐릭터 정본을 따른다.

크레파스 적용 요청에서 허용하는 범위는 지정한 화면의 기존 배경 일러스트·장식·윤곽·
색면·질감을 손그림 표현으로 조정하는 것이다. 예를 들어 기존 주방 배경은 장면과 배치를
유지해 크레파스 표현으로 바꿀 수 있지만 단색 면으로 없애지 않는다. 카드 외곽선과 장식은
변경할 수 있지만 카드의 정보 묶음과 버튼 위치는 유지한다. 필수 정보 뒤에는 질감을 넣지
않으며 읽기 어려워진 표현은 장식의 강도부터 조정한다. UI 전체를 손글씨로 바꾸지 않는다.

탭 개편, 화면·섹션 재배치, 카드 제거, 입력 단계 통합, 기능 숨김, API 확장, 새로운 상호작용
도입은 **별도 구조·동작 변경**이다. 해당 범위를 명시한 사용자 요청이 있을 때만 수행한다.
이미 요청된 범위를 다시 승인받을 필요는 없지만, “크레파스 적용”, “직관적으로”, “규칙 준수”만으로
구조 변경까지 허용됐다고 해석하지 않는다. 접근성·결함 수정도 필요한 최소 범위로 한정하고
사유와 영향을 기록하며 주변 화면의 재설계로 확대하지 않는다.

공유 토큰·공통 컴포넌트 수정 전에는 영향을 받는 화면을 확인한다. 국소 표현에는 기존 기본값을
유지하는 선택적 변형을 우선하며, 전체 앱에 전파되는 기본값 변경은 해당 범위가 요청된 경우에만
한다. 한 화면 수정이 다른 화면·Admin의 배치나 기능 색상을 바꾸지 않게 한다.

## 2. 정본 구조

| 대상 | 정본 | 역할 |
|---|---|---|
| 색상·간격·타입·크기·모션·폭·고도 | `packages/shared/src/design` | 실행 가능한 값과 CSS bridge |
| UI 행동·정보 위계·문구 | 이 문서 | 제품 전체 설계 기준 |
| 장고 외형·mood·에셋 사용 | `docs/JANGO_CHARACTER_STYLE_GUIDE.md` | 캐릭터 전용 기준 |
| 작은 화면·태블릿·큰 글자 QA | `docs/mobile-responsive-qa.md` | 검증 조합과 합격 기준 |
| 모바일 구현 | `apps/mobile/src/components` | React Native 공통 컴포넌트 계약 |

새 디자인 값은 먼저 공유 토큰에 추가한다. 앱 내부 상수나 CSS 변수로 같은 의미를 다시
정의하지 않는다. 프레임워크 변환만 각 앱의 theme facade 또는 CSS bridge에서 허용한다.

## 3. 색상 역할

모바일의 브랜드 영역은 v18 크레파스의 아이보리·민트·살구색 감성을 따른다. 밝은 브랜드
강조와 짙은 CTA·링크를 분리하며, 캐릭터 전용 색상은 `characterColors`에서 관리한다.
캐릭터 색을 버튼·오류 등 기능 색상에 직접 대입하지 않는다. UI 표현을 바꿀 때는 공유
semantic token의 역할과 대비를 검증하고 모바일 전용 표현과 공통 값을 구분한다.
유통기한 신호·오류·경고·OAuth 고유 색의 의미와 Admin의 기존 기준은 유지한다.

색은 모양이 아니라 **사용 목적**으로 선택한다.

- `background`, `surfaceWarm`, `mutedSurface`, `insetSurface`: 장고 일러스트와 이어지는
  크림 계열 화면 깊이. 흰 `surface`는 카드·시트·입력처럼 명확한 작업 면에만 사용
- `brandAccent` 계열: 진행 표시, 큰 장식, 차트처럼 텍스트를 올리지 않는 브랜드 강조
- `primaryForeground`, `linkText`: 밝은 표면 위 작은 글자·아이콘·링크
- `actionPrimaryBackground`와 `actionPrimaryPressed`: 흰 글자가 올라가는 주요 행동
- `action*Foreground`: 채워진 행동 위 콘텐츠. 흰색이더라도 `surface`로 대신하지 않음
- `dangerForeground`, `warningForeground`, `successForeground`, `infoForeground`: 상태 글자와
  작은 아이콘
- `action*Background`: 흰 글자가 올라가는 상태별 선택·행동
- `*Soft`: 상태 컨테이너 배경. 같은 상태의 `*Foreground`와 함께 사용
- `expiry*`: 유통기한 신호 전용. 일반 성공·오류·파괴 행동 토큰과 섞지 않음
- `borderSubtle`: 카드와 구분선, `borderControl`: 입력·선택 경계, `focusRing`: 현재 초점

밝은 500 단계 색을 작은 글자나 흰 글자 버튼 배경으로 사용하지 않는다. 기존
`primary`, `danger`, `warning`, `success`, `info` 별칭은 호환을 위해 남겨 두되 안전한
전경색으로 해석한다. 새 코드는 구체적인 역할 이름을 사용한다.

일반 크기 텍스트는 배경과 4.5:1 이상, 큰 텍스트와 의미 있는 비텍스트 UI는 3:1 이상
대비를 유지한다. 상태는 색 하나로만 전달하지 않고 텍스트·아이콘·형태 중 하나를 함께 쓴다.

신호등과 상태 필터는 `hasData`, `selected`, `disabled`를 별도 상태로 취급한다. 비선택은
고유 색의 soft 면과 낮은 강조로 표현하고, 무채색은 실제 비활성·사용 불가 상태에만 쓴다.
유통기한 램프의 밝은 코랄·옐로·라임 위 glyph는 공통 차콜 전경을 사용한다.

## 4. 기초 토큰

- 간격은 공유 8pt scale과 4px micro-step만 사용한다.
- 글자 크기·행간·굵기는 `typography` 역할을 한 세트로 적용한다.
- 모서리는 `radius`, 조작 높이는 `controlSize`를 사용한다. 모든 실제 터치 영역은
  `controlSize.minimum` 이상이어야 한다.
- 화면 폭은 `contentWidth`, 전환 시간은 `motion`, 투명도는 `opacity`, 그림자는
  `elevation` 역할을 사용한다.
- opacity로 필수 정보의 대비를 낮추지 않는다. disabled 상태처럼 접근성 기준의 예외가
  명확한 경우에만 사용한다.
- 장식 애니메이션은 운영체제의 동작 줄이기 설정에서 제거하거나 즉시 완료 상태로 바꾼다.

### 모바일의 크레파스 표현과 글꼴

- 홈의 장고 안내, 첫 사용 안내, 실제 빈 화면, 의미 있는 작업 완료 장면에는 v18의 손그림
  선·작은 색칠·기호를 적용하되 기존 장면·구도·시각적 깊이를 보존한다. 배경을 단색으로
  교체하거나 장식을 삭제하는 것을 크레파스 적용으로 간주하지 않는다.
- 목록·입력·재료 이름·날짜·수량·버튼·탭·오류 안내는 선명하게 정렬한다. 필수 정보 뒤에
  질감을 넣지 않으며 터치 영역과 조작 위치를 일정하게 유지한다.
- 기본 UI 글꼴은 **Pretendard**다. **Gaegu**는 장고의 짧은 인사·완료 표현 같은 브랜드
  보조 문구에 제한한다. 필수 안내와 행동은 일반 UI 글자로도 제공한다.
- 홈의 기존 카드·말풍선·배경과 영역 구분을 유지한다. 여백·제목으로 위계를 보완할 수 있지만
  단순화를 이유로 기존 정보 묶음을 해체하거나 카드 구성을 일괄 제거하지 않는다.
- 색·간격·글자·모션과 장식 변형은 공유 토큰·공통 컴포넌트로 관리한다. 아직 없는 토큰이나
  컴포넌트는 필요한 구현 작업에서 추가하며 화면별 임의 값으로 복제하지 않는다.
- 캐릭터는 [v18 MASTER 목록](../design/jango/master-set.json)에서만 파생한다. 원본 바이트,
  비율·얼굴·장갑·입 규칙을 보존하며 화면에 맞추려고 원화를 다시 그리거나 늘이지 않는다.

## 5. 화면 구성과 행동 위계

한 작업 맥락에서 시각적으로 가장 강조할 행동을 정한다. 이는 화면 전체의 기능 개수 제한이
아니다. 홈처럼 독립 과업이 함께 있는 화면은 기존 바로가기·행동을 유지한다. 아래는 위계 평가
기준이며 기존 화면의 섹션을 이 순서로 재배치하는 지시가 아니다.

1. 맥락: 사용자가 어디에 있는지
2. 가장 중요한 현재 상태: 기한, 스캔 결과, 오류, 진행 단계
3. 주요 행동: 지금 완료할 다음 행동 하나
4. 핵심 콘텐츠
5. 현재 맥락에서 필요한 보조 행동과 기존 바로가기
6. 상업·프로모션 요소

강조 경쟁은 먼저 색·굵기·설명으로 조정하며 기존 카드나 기능을 숨겨 해결하지 않는다. 주요 행동은
채워진 `primary`, 보조 행동은 `secondary` 또는 `surface`, 되돌리기 어려운 행동은
`danger`, 빈도가 낮은 행동은 텍스트 링크나 메뉴를 쓴다. 광고·제휴·구독 요소는 핵심 작업을
완료하기 전에 주요 행동보다 강하게 보이면 안 된다.

새 카드와 중첩을 추가할 때는 정보 묶음·독립 행동의 필요성을 설명한다. 기존 카드·테두리·
그림자·배경색의 조합은 앱의 시각적 특징으로 존중하며, 중복 강조를 줄인다는 이유로 일괄 제거하지 않는다.

새 선택 사항의 점진적 노출은 검토할 수 있지만, 기존 필터·설정을 접거나 메뉴로 옮기는 일은
구조 변경으로 구분한다. 문구 중복은 필요한 상태 안내를 유지하는 범위에서 줄인다.
입력 중 이탈·복귀의 보존 범위와 취소·재시도·실행 취소를 함께 설계하고, 작은 화면·큰 글자·
키보드에서도 핵심 행동이 가려지지 않게 한다. 계정·냉장고가 바뀌면 이전 맥락의 입력이나
처리 결과를 새 맥락에 잘못 적용하지 않는다.

## 6. 공통 컴포넌트 계약

### AppText

본문은 자연스러운 대화체를 사용할 수 있지만, 색과 타입은 `variant`와 `tone`으로 표현한다.
호출부에서 숫자형 font size·line height·weight를 덮어쓰지 않는다. 상태 tone은 항상 접근성
전경 역할에 매핑한다.

### Button

- 같은 작업 맥락의 경쟁하는 행동은 강조 순위를 구분한다. 화면 전체에 버튼 한 개만 남기거나
  독립 과업의 바로가기를 제거하는 규칙으로 사용하지 않는다.
- `loading` 중에는 중복 실행을 막고 busy 상태를 접근성 API에 전달한다.
- 아이콘만으로 행동을 설명하지 않으며, 아이콘 버튼은 명시적 접근성 이름을 가진다.
- 파괴 행동은 대상과 범위를 버튼이나 바로 앞 확인 문구에 밝힌다.

### EmptyState와 FeedbackBanner

- 실제 데이터가 없는 첫 상태에는 대표 장고와 첫 행동을 제공한다.
- 검색·필터 결과 없음은 기존 데이터가 없다는 뜻이 아니므로 간결한 아이콘/텍스트 상태를 쓴다.
- 오류에는 복구 행동을, 권한 문제에는 필요한 다음 단계를 제공한다.
- 첫 등록·재료 저장·재료 사용·요리 완료처럼 지정한 주요 작업의 성공에는 장고 반응을
  사용할 수 있다. 아래 상호작용 규칙에 따라 실제 결과가 확인된 뒤 표시한다.
- 그 밖의 일시적인 토스트·인라인 알림에는 장고를 기본 노출하지 않는다. 모든 성공 알림에
  캐릭터를 붙이거나 같은 결과를 말풍선·배너·토스트로 중복 알리지 않는다.
- 화면의 주 장고 안내는 하나다. 홈 안내와 완료 피드백도 서로 경쟁하지 않게 전환한다.

### Screen, BottomSheet, FormField

- `Screen`이 safe area, 키보드, 콘텐츠 폭, 하단 고정 행동을 소유한다.
- `BottomSheet`는 제목, 닫기 방식, 스크롤, footer 행동을 공통 계약으로 제공한다.
- 저장·동의처럼 반드시 선택해야 하는 sheet는 배경 탭으로 닫히지 않는다.
- 입력은 보이는 label을 가지며 placeholder만으로 의미를 설명하지 않는다.
- 오류는 해당 입력과 연결하고, 제출 실패 시 첫 오류를 읽거나 포커스할 수 있어야 한다.

## 7. 상태와 피드백

모든 데이터 영역은 loading, empty, error, ready 상태를 명시한다. mutation은 pending, success,
failure와 재시도/되돌리기 가능 여부를 함께 설계한다.

- loading: 기존 콘텐츠가 있으면 유지하고 갱신 상태만 덧붙인다.
- empty: 사용자가 만들 수 있는 첫 콘텐츠로 연결한다.
- search empty: 검색어·필터 해제 행동을 우선한다.
- error: 원인을 추측해 단정하지 않고, 안전한 재시도나 이전 화면을 제공한다.
- success: 결과를 본문에 반영하고 일시 알림을 중복 사용하지 않는다.
- destructive: 대상 이름과 개수를 확인하고, 가능한 경우 되돌리기를 제공한다.

### 모바일 장고 상호작용

장고는 **안내 → 처리 중 → 결과 확인·복구**처럼 의미 있는 순간에 함께한다. 주요 작업의
반응은 기존 조회·변경 결과에서 계산하며 별도의 대화 API나 서버 상태 저장소를 전제로 하지 않는다.

- 첫 등록, 재료 저장·사용, 요리 완료의 성공 반응은 서버 저장 성공이 확인된 뒤에만 보낸다.
  버튼을 누른 시점, 낙관적 화면 변경, 요청 중 상태를 성공으로 표현하지 않는다.
- 같은 작업의 반복 탭·재요청·재조회로 축하를 중복 재생하지 않는다. 화면 이탈·로그아웃·
  계정 또는 냉장고 전환 시 이전 반응을 취소하고 늦게 도착한 결과도 현재 맥락과 대조한다.
- 화면당 주 안내 하나를 유지한다. 장고를 누르는 반응이 있어도 기능은 명시적인 버튼으로
  항상 접근할 수 있어야 한다. 오류에는 복구 행동을 함께 제공한다.
- 포즈 전환과 짧은 이동·회전으로 반응한다. 원화를 변형하거나 상시 반복 동작을 만들지
  않는다. 키보드 입력·조리 중에는 장식을 줄이며 애니메이션을 기다려야 작업할 수 있게 하지 않는다.
- 동작 줄이기에서는 정적인 결과를 보여준다. 화면 읽기에는 상태를 한 번 전달하고 장식
  이미지와 말풍선이 같은 안내를 중복 낭독하지 않게 한다.
- 현재는 `Mascot`·`MascotSpeechBubble`의 기존 계약을 사용한다. 향후 공통 반응 컴포넌트를
  별도 요청으로 도입하는 경우에도 화면마다 다른 말풍선·애니메이션 체계를 복제하지 않는다.

## 8. UX 문구

설명·안내·장고 대사는 “재료 3개를 넣었어요”처럼 다정하고 짧은 존댓말을 유지한다. 버튼, 탭,
메뉴, 접근성 행동 이름은 결과가 바로 드러나는 짧은 표현을 쓴다. 행동 버튼은 “재료 넣기”,
“사용했어요”, “이 재료로 요리 추천받기”처럼 실행 결과를 예상할 수 있어야 한다.

| 피할 문구 | 권장 문구 |
|---|---|
| 이 날짜로 할게요 | 날짜 선택 |
| 다시 불러올게요 | 다시 시도 |
| 다음 재료 넣을게요 | 다음 재료 추가 |
| 네, 정리할게요 | 계정 삭제 |
| 그만 추가할래요 | 추가 완료 |

확인 질문은 본문에 쓰고 버튼에는 선택 결과를 쓴다. “확인”, “알겠어요”만으로 결과가 불명확한
경우 구체적인 동사를 사용한다. 파괴 행동에는 완곡한 표현을 쓰지 않는다.
날짜는 “D-2” 같은 약어만으로 설명하지 않고 “2일 남음”처럼 읽기 쉬운 말을 함께 제공한다.
확인일은 섭취 가능 판정으로 표현하지 않으며 재료 폐기에 죄책감을 주는 말투를 사용하지 않는다.

## 9. 반응형·접근성·Admin

- 320px급 작은 화면, phone landscape, regular-width/tablet, system font scale 1.0/1.3/2.0을
  기본 검증 조합으로 삼는다.
- 글자가 커지면 잘라내기보다 세로 stack, 줄바꿈, 스크롤을 우선한다.
- 모바일과 Admin은 같은 semantic token을 사용하되 플랫폼 고유 내비게이션 패턴은 유지한다.
- Admin도 최소 조작 높이, focus-visible, 키보드 순서, 상태 대비 기준을 동일하게 적용한다.
- 브라우저 기본 focus를 숨기지 않는다. 모달과 sheet는 열림·닫힘 시 포커스 흐름을 보존한다.

## 10. 변경과 검증

새 화면은 기존 앱의 구도·시각 언어, 공통 컴포넌트와 의미 토큰으로 시작한다. 화면에서 반복되는 패턴이 세 번째로
등장하기 전에 공통 컴포넌트로 승격한다. 정본 변경에는 다음 검증을 함께 갱신한다.

- 공유 토큰 단위 테스트: 색 대비, 크기·모션 순서, CSS 변수 bridge
- 모바일 디자인 계약 테스트: raw 값 금지, 공통 컴포넌트 역할 매핑
- Admin 디자인 계약 검사: 모호한 전경색과 접근성 낮은 액션 조합 금지
- 관련 화면 테스트와 작은 화면·큰 글자 layout screenshot 비교
- 변경 전후 핵심 과업의 완료율, 이탈 단계, 오류·재시도율 비교

기존 디자인 계약 검사와 CI는 유지한다. 문서 검사는 정본·링크, 디자인 계약 검사는 토큰·
컴포넌트의 기계적으로 확인 가능한 조건을 검증한다. **시각적 위계·감정 전달·다음 행동의
명확성은 화면 검토 대상이며 자동 검사 통과가 디자인 승인을 대신하지 않는다.** 실제 측정
전에는 사용성이 개선되었다는 수치를 주장하지 않는다.

향후 UI 변경 기록에는 다음 근거를 남긴다. 실행하지 못한 검증은 통과로 쓰지 않고 이유를 명시한다.

- 요청 범위, 기준 화면·커밋, 보존할 요소, 실제 변경 요소와 적용 규칙
- 공유 토큰·컴포넌트의 영향 화면과 변경하지 않은 화면의 회귀 확인
- 별도 구조·동작 변경이 있다면 이를 요청한 근거와 과업·탐색에 미치는 영향
- 같은 화면 크기·상태에서의 변경 전후 화면
- 로딩·빈 상태·오류·완료·처리 중 등 관련 주요 상태와 복귀·취소·재시도·실행 취소 결과
- 작은 화면·큰 글자·키보드·화면 읽기·동작 줄이기 등 관련 접근성 확인 결과
- 장고 반응을 바꾼 경우 서버 성공 전 노출, 중복 재생, 이전 계정·냉장고 결과 차단 확인

장고 정본 문서의 해시가 바뀌면 [검수 절차](../design/jango/quality/README.md)에 따라
`pnpm jango:reports:refresh`로 현재 보고서를 갱신한다. 과거 준비·제작 기록과 MASTER 이미지,
재검토 상태·서명 여부는 보존한다. 보고서 갱신을 소급 승인으로 취급하지 않는다.

제품 분석 이벤트를 새로 수집하기 전에는 개인정보 고지와 동의 범위를 먼저 확인한다. 그 전까지는
동의받은 사용성 세션과 기존 집계 데이터만 사용하며, 개인을 식별하는 새 속성은 추가하지 않는다.
사용성 회귀는 아래 핵심 과업을 같은 시작 상태와 기기로 각각 5회 이상 수행해 비교한다.

| 핵심 과업 | 완료 조건 | 함께 기록할 신호 |
|---|---|---|
| 재료 등록 | 사진·바코드·직접 입력 중 하나로 저장 완료 | 완료율, 소요 시간, 되돌아간 단계, 입력 오류 |
| 재고 찾기·수정 | 목표 재료를 찾아 수량 또는 기한 저장 | 검색·필터 재시도, 잘못 누른 행동, 저장 실패 |
| 추천·조리 | 추천 생성 후 첫 조리 단계를 시작 | 추천 이탈 단계, 재시도, 개인정보 안내 이해 여부 |
| 공간 참여·전환 | 초대 수락 후 대상 공간으로 전환 | 코드 오류, 권한 혼동, 전환 실패 |
| 구독·복원 | 상품 이해 후 구매 또는 복원 결과 확인 | 상품 선택 혼동, 취소·실패 단계, 복원 성공 |

각 세션은 과업 성공 여부, 완료 시간, 오류·재시도 횟수, 첫 화면을 5초 본 뒤의 “다음 행동” 설명을
기록한다. 접근성 검증 세션에는 화면 읽기 또는 큰 글자 사용자 사례를 최소 하나 포함한다.

표현 변경의 완료 기준에는 기존 앱으로 인식되는 시각적 연속성, 실제 크레파스 표현의 확인,
기존 과업·접근성의 비퇴행을 함께 포함한다. 테스트 통과나 장고 이미지 교체만으로 그림체
적용이 완료됐다고 보고하지 않는다. 사용성 개선은 실제 관찰·측정 근거가 있을 때만 주장한다.

## 11. 취소한 개편과 이후 작업 순서

4개 탭 전환·상단 내 정보 이동, `JangoCompanion` 도입, 홈 요약 API 확장을 포함한 이전
앱 전체 개편 계획은 롤백과 함께 철회했다. 후속 구현 목표나 미완료 과제로 자동 재개하지 않는다.
현재 5개 탭과 기존 `Mascot`·`MascotSpeechBubble`은 임시 호환 상태가 아닌 현행 기준이다.

표현 작업은 **기준 화면 확인 → 같은 구도의 대표 화면 시안 → 전후 시각 검토 → 요청 범위에 적용**
순서로 진행한다. 먼저 홈 등 대표 화면 하나에서 기존 정보·조작·구도가 유지되고 크레파스의
선·색면·질감이 실제로 보이는지 확인한다. 구조 변경이 필요해졌다면 표현 변경과 분리해
구체적인 전후 화면·이유·영향을 제시한다. 시안 검토 없이 앱 전체의 기본 스타일로 확산하지 않는다.

화면 비교는 같은 데이터·상태·크기에서 수행하며, 의도한 표현 변경과 예상 밖의 레이아웃 변화를
구분해 기록한다. `approve-mobile-layout-change` 라벨은 검토한 시각 변경의 표시일 뿐
사용자 요청 범위 확대나 디자인 승인 근거가 아니다. 자동 검사·캡처 생성만으로 검토를 완료했다고
하지 않는다. 실제 사용자 검증이 없다면 미실시로 기록한다. 원격 배포는 별도 작업이다.
