# 사진 등록 품질 개선 — 2026-11-01

**2026-11-06 후속:** 승인된 출시 작업에서 사진15장 전체를 같은 해시로 확보하고 v1/v2
실호출30회를 완료했다. 결과는 일부 누락 개선과 잔여 수량·브랜드 오류 및 회귀가 혼재한다.
[비교 결과·비용·검증 한계](../release-1.4.5/verification-20261106/README.md)를 참고한다.
아래는11월1일 코드 작업 당시의 기록이며 네이티브 전처리 검증 한계는 유지한다.

승인 범위는 코드·검증·기록이다. 커밋·푸시·서버/DB 운영 배포·스토어 출시는 실행하지 않았다.
기존 장고 크기 복원 및 생활 공간 배경 v2를 보존한다.

## 확인한 원인과 수정

- 중복 키에 브랜드와 기준 단위가 없었다. 이름·브랜드·표시 단위·기준 단위·자리·기한을 비교하며
  다른 브랜드·규격·단위는 제외한다. 브랜드 불명은 `possible` 참고 안내로만 표시하고 저장을
  막지 않는다. 동일 브랜드까지 확인되는 `exact`에는 합치기·별도 추가·제외를 유지한다.
- 영수증 합계·할인·봉투 필터가 냉장고에도 적용됐다. 영수증에만 한정한다.
- 기한 지정과 별도 추가가 `needsReview`까지 해제했다. 해당 행동은 AI 검토를 유지하고 명시적
  내용 확인만 해제한다. 합치기는 양쪽의 내용 확인·완성도 및 표시/기준 단위 호환을 확인한다.
- “겹쳐 보여요”는 보관함 동일 정보 / 사진 결과 반복으로 구분한다. 부분 가림의 AI 이유도
  중복 안내와 함께 남긴다. 기존 카드·상세 화면·단계·탭·접근성·장고·배경 구성은 유지한다.

촬영·앨범 품질은 1.0으로 받는다. SDK54 호환 `expo-image-manipulator ~14.0.8`,
`expo-file-system ~19.0.24`로 디코딩/방향 반영 → 비율 유지 긴 변 최대2560 → JPEG 90%를
사용한다. 4MiB(4,194,304바이트) 초과 시 같은 크기 80%, 이후 최대2048·80% 순서이며 작은
사진은 확대하지 않는다. 모두 초과하면 전송 전에 안내한다. 렌더된 이미지에서 다시 저장하므로
앞서 압축한 JPEG를 재압축하지 않는다. 원본은 지우지 않고 생성 파일만 multipart 종료 후 또는
오류·계정/냉장고 변경 때 정리한다. 기존 서버의 APP1 Exif 제거를 유지한다.

냉장고 프롬프트 v2는 선반/앞뒤/문 안쪽 순회, 식별 가능한 부분 가림, 읽히는 브랜드·규격,
별개 포장 수를 지시한다. 완전히 숨은 물건·읽히지 않는 브랜드·추정 기한은 금지한다.
같은 모델·한 번의 호출·30개 후보를 유지하며 기본 출력 상한만1800→4096으로 늘린다.
영수증 지침 문장은 기존과 동일하다. 출력 잘림은 부분 결과 저장 없이 실패하며 자동 재호출하지 않는다.

## 실제 인식 비교: 미완료

[재확보 결과](reacquire.json), [비교 계획/원본 해시](live-manifest.json),
[요청 결과](live-results.jsonl), [정산 중단](live-settlement.json), [재현 스크립트](compare.mjs).

기존 승인 공개 사진15장의 URL·라이선스·SHA256은 기존 정본
`docs/operations/ai-evaluations/current-baseline-2026-10-20/photo-provenance.json`을 재사용한다.
7장(01·02·03·09·11·12·13)은 동일 바이트로 재확보했다. 나머지8장은 Wikimedia HTTP429로
재확보하지 못했고 해시가 다른 대체 사진을 넣지 않았다. 원본은 저장소 밖 임시 경로에 둔다.

같은 사진·같은 모델 `gpt-5.6-luna`로 v1/v2를 번갈아14회 호출하도록 준비했다. 모델은 현재 코드
기본값과 승인된 기존 평가의 모델이며 로컬 dev의 `gpt-4.1-mini` 지정은 평가에 사용하지 않았다.
운영 환경의 모델 override는 이번 작업에서 확인하지 않았다. 비교는 서버 프롬프트/필터/출력 상한
차이이며 네이티브 전처리 효과를 포함하지 않는다. v1은 작업 시작 HEAD의 원본 소스·해시로 고정한다.

첫 분석 요청이 `provider_config`로 실패했다. 추가 유료 분석 없이 모델 메타데이터를 조회해
HTTP401 `invalid_api_key`를 확인했다. 사용량이 보고되지 않아 보수적으로 평가를 중단했다.
분석 요청1회, 성공0회, 보고된 사용량 없음, 계산된 비용0달러(확정 청구 내역 아님)다.
최대60회·총1달러 제한을 유지했으며 추가 분석·모델 교체·운영 키 복사는 하지 않았다.
따라서 누락·오인식·수량 오류의 전후 수치와 실제 정확도 개선은 확인하지 못했다.
불확실한 기존 정답(예:13번 녹색 채소)을 채점하거나 모의 테스트를 정확도 지표로 사용하지 않는다.

## 적용 시 필요 사항

- 모바일 새 네이티브 빌드가 필요하다. JS OTA만으로 모듈을 제공할 수 없다. 기존 공식 네이티브
  동기화/빌드 경로로 dependency autolinking과 Pod/Gradle 반영 후 실기기에서 확인해야 한다.
- API 코드를 추후 배포할 때 환경의 `INVENTORY_PHOTO_PARSE_MAX_OUTPUT_TOKENS` 지정이
  1800이면4096으로 맞춰야 한다. 이번에는 `.env.example`만 변경했고 실제 로컬/운영 env는
  수정하지 않았다. 모델·비용 한도·광고·구독·분석 횟수·동의·소유권·멱등성·DB/API 계약은 유지한다.
- 유효한 개발용 API 인증과 나머지8장 원본 확보 후 동일 해시·동일 모델 평가를 마쳐야 한다.
  실패한1회를 포함해 총60회·1달러 한도를 적용하고, 사용량 불명은 먼저 대조한다.
